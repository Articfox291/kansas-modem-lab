What is stopping actual code execution on the coprocessor

Headline first: execution itself is NOT blocked — signed arbitrary patches boot clean today (force-1 is running on slot A right now). What stands in the way is useful, verified-before-flash, goal-directed execution. Wall by wall:
BREACHEDImage signing (CERT2). Hash-override re-sign + fastboot flash accepted, byte-identical reproducibility (sha 7ed179…). The modem runs our bytes. This wall fell first and stays down as long as slot-B-stock + backup discipline holds.
STANDINGSecure-boot anchors below the modem. BootROM (eFuse PKI) → preloader (no CERT2 container — re-sign refused by design) → LK (separate unlock-serial flow). We can sign modem code, not rewrite the chain of trust. A bad preloader/LK flash = unrecoverable brick; those regions are permanently off-limits.
STANDINGFail-closed silicon behavior. Bad NVRAM → lid_error_handle.c:161 → BREAK → MD exception → WDT reset loop (proven live, twice observed). Bad code → same exception path. The modem does not limp past corruption — every untested payload risks an exception loop recoverable only by reflash. This is the tax on each live experiment.
STANDINGNo full-system rehearsal. Nothing boots the modem off-device: no MMU/TLB model, no Nucleus scheduling, no DSP, no RF, no interrupts-as-hardware. Carved-function proofs (25-step stock, 1-step patch) validate instructions, never consequences. Every flash is therefore a first live run — the gap between "executes" and "behaves" can only be closed on silicon, one risky cycle at a time.
STANDINGHardware-bound secrets. SML plaintext, NCK material, HCK keys, eFuse/OTP, RPMB, TEE (MobiCore/Trusty) — decryption happens behind silicon the PCORE code calls into but never sees. Even with arbitrary code execution, secrets come out as oracle answers (yes/no), never bytes. Exfiltration is architecturally impossible, not merely unattempted.
STANDINGAttempt counters + irreversible latches. remain 5 (floor), retry 5→0→sticky HARD_LOCKED, DISABLE_PERMANENT latch. These live in protect/NVRAM the modem itself guards; brute force is mathematically closed and each probe is priced. Our NCK work is RAM-only forever.
PARTIALIn-firmware validators + dispatch bounds. Analyzer 0..442, BGEIUC/ANDI gates, validator caps, guard fixtures — all hold under faithful models, which is exactly why H1 needs a 3-conjunct bypass and H2 needs a second bug. They don't stop our signed patches, but they stop every input-driven path (AT text, ring bytes, staged SMEM) from reaching a write primitive — proven DoS-only for JRC, OPEN-but-narrow for op12.
PARTIALAnalysis darkness around the payload. JALRC real targets unrecoverable in isolation (need live RAM), esmlck/verify run on synthetic ret1, SWM/XS/INS fixes unapplied, EARFCN path + modem RPC/FSD consumers unlisted. We can execute anywhere and understand ~90% of the lock path — but a payload touching unknown callees flies blind past its BALC. Each wave shrinks this; it is the only wall that yields to decomp.
STANDINGDSP + RF physics. Different ISA with no toolchain, closed-loop gain the PCORE can't observe, synth lock ranges, duplexer roll-off above 915 MHz. No patch makes a filter pass what it rejects. Code execution ends at the PCORE pins; radiation obeys hardware.
STANDINGProcedure, not silicon: slot discipline + backups + floors. Slot B stock, protect/nvram backups, remain-5 floor, no-reboot/no-write rules for reads, dry-run-only flash planning. These stop us from bricking ourselves — the only adversary that has ever damaged this modem (protect-erase incident) was us.

Net assessment

QuestionAnswer
Can we execute code on the coprocessor?Yes — today. Signed patches boot clean; force-1 proves control flow hijack at will.
Can we execute the right code first-try?Not reliably. No full-system rehearsal + analysis darkness ⇒ each novel payload is a live experiment priced in flash cycles and exception-loop risk.
Can code exec read protected data?No. HW-bound crypto answers yes/no; bytes never surface. Architectural, permanent.
